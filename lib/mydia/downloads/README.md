# Downloads: trackerless releases

## Two paths let a trackerless release reach the client

Both stall at exactly 0 bytes wherever DHT cannot reach the swarm. On galactica,
transmission runs inside the PIA VPN netns, where DHT yields no peers while
`udp://` trackers work fine.

**Magnets**, fixed 2026-08-04 in getmydia/mydia#331. Bitmagnet always emits a
bare `magnet:?xt=urn:btih:HASH&dn=NAME`, and Prowlarr does whenever `/download`
302s to a magnet. `TorrentHash.ensure_trackers/1` now appends the 8
`@public_trackers`, called at the exit of `TorrentFetch.prepare_torrent_input/2`. Before the
fix, rqbit with magnets completed 26 of 26 while transmission with magnets
completed 0 of 23.

**`.torrent` files**, fixed 2026-08-13 in getmydia/mydia#440. The #331 fix only
matched `{:ok, {:magnet, _}}`, while `classify_body/1` returns
`{:ok, {:file, body, :torrent}}` for a bencoded torrent, which fell through the
`other -> other` catch-all. `ensure_trackers/1` also has a catch-all
`def ensure_trackers(other), do: other`, so it is a silent no-op on a binary.
Prowlarr's 1337x `/download` served a real `.torrent` generated by go.torrent
(`created by: go.torrent`, `comment: dynamic metainfo from client`) carrying no
`announce` and no `announce-list`. `TorrentHash.ensure_torrent_trackers/1` now
splices both keys into the front of the top-level bencode dict, at the correct
lexicographic position. The `info` dict is never touched, so the info hash stays
byte-stable.

## Telling trackerless apart from a dead swarm

Trackerless looks like this: transmission reports `trackers=[]`, `peersFrom` is
zero from every source including `fromDht`, yet `metadataPercentComplete=1.0` and
`totalSize` is known. Complete metadata with zero peers ever connected is only
possible from a `.torrent` file, which proves the file arrived trackerless rather
than a magnet failing to fetch metadata. Cross-check `downloads.metadata` for the
indexer's `seeders`; a high count there means the swarm is alive and only the
tracker list is missing.

A dead swarm looks different: trackers are present and announcing
(`lastAnnounceSucceeded=true`) but report `seederCount=0` with only leechers.

Already-stalled torrents are not retroactively fixed by either code change. They
need trackers added in the client, or a re-grab.

## Seeding guard and share limits

Tracker terms frozen at grab (`Download.metadata["tracker_terms"]`, see
`lib/mydia/indexers/README.md`, "Tracker terms") set a seeding goal: a minimum
ratio, a minimum seed time, or both, met by whichever comes first.
`Mydia.Downloads.SeedingGoal` owns the rule. Terms that ask for nothing leave
removal as it was; a private tracker with no known ratio or seed time is never
met, so its downloads are only ever removed by hand.

**Guard.** `ClientRemoval.terms_met?/2` runs before the idle-state check in
both `maybe_remove_after_import/1` and `finish_pending_removal/2`, for the
clients `ClientRemoval.seeding_client_type?/1` names: qBittorrent, Transmission,
rTorrent and rqbit. That matters most for rqbit, which is not seed-aware and was
removed right after import. A guarded row returns `:still_seeding` and stays in
`list_pending_removals/1`. SABnzbd, NZBGet, debrid, blackhole (an external
client with no ratio to read) and unknown types are not guarded. A torrent the
client no longer has is still stamped removed.

Seed time is `DownloadStatus.seeding_time` when the client counts it
(qBittorrent `seeding_time`, Transmission `secondsSeeding`). For rTorrent
and rqbit, which count none, `Mydia.Downloads.ObservedSeedTime` adds up the time
`DownloadMonitor` sees the torrent seeding between polls (a gap longer than
three cron intervals credits nothing, so downtime is not counted) in
`Download.metadata["observed_seeding"]`, and that total stands in for it, so a
torrent that seeded past its goal and then stopped is removable. Without either,
and only while the client reports the torrent as seeding, it is the time since the
client's `completed_at`, else since `Download.completed_at`. A paused, stopped or
missing torrent with no reported time has no known seed time, so wall-clock time
it spent not seeding never meets a goal.

**Limits.** At grab, `Mydia.Downloads.SeedingLimits` sends the goal through the
optional `set_share_limits/3` adapter callback, best effort. qBittorrent gets
`ratioLimit` and `seedingTimeLimit` (minutes, rounded up), with `-1` rather than
`-2` for the unset one so a global limit cannot stop a torrent short of a
seed-time goal. Transmission gets `seedRatioLimit` with `seedRatioMode=1`; it
has no total seed time limit, so a seed-time-only goal is left on the global
ratio mode. Neither alternative is better: mode 1 needs a ratio, and mode 2
(unlimited) never pauses, which keeps Remove After Import waiting forever. If
the global ratio stops such a torrent early, the guard keeps it in the client.
rTorrent and rqbit get nothing. A failed push is
logged and the guard still applies.

**Manual removal is never guarded.** The Downloads page's cancel and clear
confirms and the media page's cancel dialog add a hit-and-run warning while the
goal is unmet (`MydiaWeb.SeedingComponents`). Deleting a media item does not
touch the client (its downloads rows cascade away and the torrent keeps
seeding), so it needs no warning.

## Built-in client

`Mydia.Downloads.BuiltIn` runs rqbit and, optionally, the VPN that tunnels it.
`BuiltIn.Config` reads the `MYDIA_TORRENT_*` and `MYDIA_VPN_*` variables and
decides auto-enable: on when `rqbit` is on the `PATH` and no qBittorrent,
Transmission, rqbit, rTorrent, Debrid or Blackhole client is configured.
`ClientRemoval` and the other config builders must carry
`connection_settings`, or `BuiltIn.managed?/1` reads the built-in client as
unmanaged and the guard below is skipped.

**Child environment.** rqbit and `torrent-curl` are spawned with every
`MYDIA_VPN_*` variable and Mydia's secrets unset
(`BuiltIn.Config.child_env_unset/1`).

**Runtime injection.** `Mydia.Settings.RuntimeConfig.get_runtime_download_clients/0`
appends `BuiltIn.client_configs/0` to the clients from env and YAML, so the
built-in client is a synthetic `rqbit` row that exists only at runtime. Its
connection settings carry `"managed" => true`.

**Managed guard.** `Mydia.Downloads.Client.Rqbit` wraps every call in
`BuiltIn.guard/1` when the config is managed. A stopped engine, a VPN that is
down or a failed leak check returns `{:error, reason}` with a named reason
instead of a connection error to loopback, so a grab fails with the cause and
`ClientHealth` shows it. Unmanaged rqbit configs skip the guard.

**State.** The engine's and the VPN's state, the listen port and the config
warnings live in `BuiltIn.Status`, which broadcasts every change for the admin
panel. `BuiltIn.Vpn` polls gluetun's control server and gates the engine on
`running` plus a passed leak check. The entrypoint's `docker/vpn-preflight.sh`
writes `/config/gluetun/preflight` before the BEAM starts; it records
`net_admin`, `tun` and `src_valid_mark`, and only the first two fail the VPN.
`src_valid_mark` is informational and Mydia does not read it yet.

In VPN mode the engine is started with `--listen-ip <tunnel IPv4>`, read from
`ip -4 -o addr show dev <iface>` as the mydia user, so that inbound UDP replies
leave the tunnel from the port the peer contacted. See
`vendor/gluetun/README.md`, "Inbound UDP needs a bound socket".
