# Downloads: trackerless releases

## Two paths let a trackerless release reach the client

Both stall at exactly 0 bytes wherever DHT cannot reach the swarm. On galactica,
transmission runs inside the PIA VPN netns, where DHT yields no peers while
`udp://` trackers work fine.

**Magnets**, fixed 2026-08-04 in getmydia/mydia#331. Bitmagnet always emits a
bare `magnet:?xt=urn:btih:HASH&dn=NAME`, and Prowlarr does whenever `/download`
302s to a magnet. `TorrentHash.ensure_trackers/1` now appends the 8
`@public_trackers`, called at the exit of `TorrentFetch.prepare_torrent_input/2`. Before the
fix, rqbit with magnets completed 26 of 26 while transmission with magnets
completed 0 of 23.

**`.torrent` files**, fixed 2026-08-13 in getmydia/mydia#440. The #331 fix only
matched `{:ok, {:magnet, _}}`, while `classify_body/1` returns
`{:ok, {:file, body, :torrent}}` for a bencoded torrent, which fell through the
`other -> other` catch-all. `ensure_trackers/1` also has a catch-all
`def ensure_trackers(other), do: other`, so it is a silent no-op on a binary.
Prowlarr's 1337x `/download` served a real `.torrent` generated by go.torrent
(`created by: go.torrent`, `comment: dynamic metainfo from client`) carrying no
`announce` and no `announce-list`. `TorrentHash.ensure_torrent_trackers/1` now
splices both keys into the front of the top-level bencode dict, at the correct
lexicographic position. The `info` dict is never touched, so the info hash stays
byte-stable.

## Telling trackerless apart from a dead swarm

Trackerless looks like this: transmission reports `trackers=[]`, `peersFrom` is
zero from every source including `fromDht`, yet `metadataPercentComplete=1.0` and
`totalSize` is known. Complete metadata with zero peers ever connected is only
possible from a `.torrent` file, which proves the file arrived trackerless rather
than a magnet failing to fetch metadata. Cross-check `downloads.metadata` for the
indexer's `seeders`; a high count there means the swarm is alive and only the
tracker list is missing.

A dead swarm looks different: trackers are present and announcing
(`lastAnnounceSucceeded=true`) but report `seederCount=0` with only leechers.

Already-stalled torrents are not retroactively fixed by either code change. They
need trackers added in the client, or a re-grab.

## Seeding guard and share limits

Tracker terms frozen at grab (`Download.metadata["tracker_terms"]`, see
`lib/mydia/indexers/README.md`, "Tracker terms") set a seeding goal: a minimum
ratio, a minimum seed time, or both, met by whichever comes first.
`Mydia.Downloads.SeedingGoal` owns the rule. Terms that ask for nothing leave
removal as it was; a private tracker with no known ratio or seed time is never
met, so its downloads are only ever removed by hand.

**Guard.** `ClientRemoval.terms_met?/2` runs before the idle-state check in
both `maybe_remove_after_import/1` and `finish_pending_removal/2`, for the
clients `ClientRemoval.seeding_client_type?/1` names: qBittorrent, Transmission,
rTorrent and rqbit. That matters most for rqbit, which is not seed-aware and was
removed right after import. A guarded row returns `:still_seeding` and stays in
`list_pending_removals/1`. SABnzbd, NZBGet, debrid, blackhole (an external
client with no ratio to read) and unknown types are not guarded. A torrent the
client no longer has is still stamped removed.

Seed time is `DownloadStatus.seeding_time` when the client counts it
(qBittorrent `seeding_time`, Transmission `secondsSeeding`). For rTorrent
and rqbit, which count none, `Mydia.Downloads.ObservedSeedTime` adds up the time
`DownloadMonitor` sees the torrent seeding between polls (a gap longer than
three cron intervals credits nothing, so downtime is not counted) in
`Download.metadata["observed_seeding"]`, and that total stands in for it, so a
torrent that seeded past its goal and then stopped is removable. Without either,
and only while the client reports the torrent as seeding, it is the time since the
client's `completed_at`, else since `Download.completed_at`. A paused, stopped or
missing torrent with no reported time has no known seed time, so wall-clock time
it spent not seeding never meets a goal. `ObservedSeedTime.record/2` returns the
polled rows with their new entry merged in, and `DownloadMonitor` hands those to
`BuiltIn.Policies`, so the first poll that tracks a torrent reads 0 observed
seconds rather than the time since completion: a seed-time target set after a
torrent finished counts from when Mydia started observing it.

The ratio needs the same help for rqbit. rqbit 9.0.1 counts `uploaded_bytes`
only while a torrent is live: it reads 0 once paused and starts again from 0
after a restart, so its adapter sets `DownloadStatus.uploaded_session_only?`.
For those rows `Mydia.Downloads.ObservedUpload.record/2`, called by
`DownloadMonitor` right after the seed time, banks the counter in
`Download.metadata["observed_upload"]` (`"bytes"` is the total, `"session"` the
counter as last seen; a counter below `"session"` is a new session and counts in
full; `"seen_at"` is when the counter that last changed them was asked for,
rqbit's `DownloadStatus.observed_at`). Overlapping passes must not add an older,
lower counter as a reset: a read no later than `"seen_at"` changes nothing, and a
lower counter counts as a reset only when read 300 seconds or more after it. The
rqbit adapter keeps the counter session-only (and stamps `observed_at`) only for a
read that finished within 120 seconds, so no read that slow can land as a reset; a
slower read is shown as rqbit reported it and is not recorded. `ObservedUpload.overlay/1` then replaces `uploaded` and `ratio` on every
enriched row (`EnrichedDownload.live_uploaded` keeps the client's own counter),
and `ClientRemoval.terms_met?/2` applies `overlay_status/2` to the status it
reads, so a torrent paused at its goal keeps its ratio and ratio goals do not
restart on each pause. On first sight the current session counts in full:
uploaded bytes are a reported fact, unlike seed time. Uploads in a session that
ended before Mydia saw it, or between the last poll and a manual pause or
restart, are lost, and so is a reset seen inside the 300 seconds when the new
session's counter passes the old one before the next pass: the total errs low,
never high, and the torrent seeds longer.

**Limits.** At grab, `Mydia.Downloads.SeedingLimits` sends the goal through the
optional `set_share_limits/3` adapter callback, best effort. qBittorrent gets
`ratioLimit` and `seedingTimeLimit` (minutes, rounded up), with `-1` rather than
`-2` for the unset one so a global limit cannot stop a torrent short of a
seed-time goal. Transmission gets `seedRatioLimit` with `seedRatioMode=1`; it
has no total seed time limit, so a seed-time-only goal is left on the global
ratio mode. Neither alternative is better: mode 1 needs a ratio, and mode 2
(unlimited) never pauses, which keeps Remove After Import waiting forever. If
the global ratio stops such a torrent early, the guard keeps it in the client.
rTorrent and rqbit get nothing (rqbit has no per-torrent limits, so the
built-in client's target is enforced by Mydia, below). A failed push is
logged and the guard still applies.

**Operator target (built-in client only).** The built-in client's `seed_ratio`
and `seed_time` settings (minutes; the target holds seconds) are a seeding goal
of the operator's own, with `seed_goal_action` (`pause` or `remove`). For a
download whose `download_client` is `BuiltIn.name()`, the goal is a
conjunction: the tracker terms must be met under the rules above, and the
target must be met by either its ratio or its seed time. The target's seed time
counts only time the client reported or `ObservedSeedTime` observed
(`SeedingGoal.counted_seed_time/1`, passed as `:counted_seed_time`), never the
wall-clock fallback above, which stays for the tracker terms alone. With
neither known, as when the first observation failed to write, the target's
seed time is unreached, so an old torrent is never paused or removed at once.
`SeedingGoal.goal_applies?/2` and `SeedingGoal.goal_met?/4` are the decision,
read by the guard, `ObservedSeedTime`, `SeedingPolicy` and the `met?` of
`for_download/2`; every other client is held to the tracker terms alone.
Neither half lowers the other: a tracker's 72 hour minimum does not release a
torrent short of a ratio 2.0 target, and a private tracker with unknown rules
is never met, so no target (a ratio of 0 included, which is a target) pauses or
removes it. The Downloads page shows the tracker requirement and the target
separately (`required_*` and `target_*` on `for_download/2`'s struct).
`BuiltIn.seeding_target/0` reads the running client's config and returns nil
without a runtime or with neither field set.

`BuiltIn.Policies`, called from `DownloadMonitor` each poll for the rows of
the built-in client, runs `BuiltIn.SeedingPolicy` on each. Once the goal is
met while the torrent is seeding: with `pause`, the torrent is paused through
the adapter and the row is stamped `metadata["seeding_goal_reached_at"]`; the
stamp makes the pause one-shot, so a torrent the operator resumes by hand is
not paused again. With `remove`, an imported row is left to `ClientRemoval`
(`BuiltIn.client_configs/0` sets `remove_completed` for a remove target, so the
normal removal path takes it, still behind the guard), and an unimported one is
paused until it is imported. An imported row with `match_status`
`"unresolved_files"` is paused and stamped too, since `ClientRemoval` skips it.
Failures are logged and never fail the poll.
Switching the action to `remove` applies to the whole backlog:
`list_pending_removals/1` picks up every imported built-in row without
`client_removed_at`, stamped or not, so the next poll removes (and deletes the
data of) each one past the goal, including torrents the operator resumed by hand.

**Manual removal is never guarded.** The Downloads page's cancel and clear
confirms and the media page's cancel dialog add a hit-and-run warning while the
goal is unmet (`MydiaWeb.SeedingComponents`). Deleting a media item does not
touch the client (its downloads rows cascade away and the torrent keeps
seeding), so it needs no warning.

## Built-in client

`Mydia.Downloads.BuiltIn` runs rqbit and, optionally, the VPN that tunnels it.
The design is `design/specs/2026-11-12-ui-builtin-torrent-vpn-design.md`.

**Configuration.** The `built_in_torrent` section of `Mydia.Config.Schema`
(`Config.Schema.BuiltInTorrent`) is layered like any other: yaml, then
`config_settings` rows keyed `built_in_torrent.<field>`, then env, which wins.
`MYDIA_TORRENT_*` and `MYDIA_VPN_*` are the env side. The section is flat
(`vpn_` prefixes) because the overlay paths are one level deep. `vpn_provider`
and `vpn_type` are trimmed, downcased strings, never atoms, and the schema does
not check them against `VpnProviders` (an env value newer than the table must
not fail the config load); `Settings.save/2` does. The two secrets are
`redact: true`. `BuiltIn.Settings` is the form's API: it skips fields whose env
var is set, never writes them, and keeps a stored secret when the field is
submitted blank. `Loader.reload/1` broadcasts `{:runtime_config_reloaded, config}`
on `Mydia.Config.Broadcast.topic/0` after every save, and skips the broadcast while
`Mydia.PubSub` is not running (boot).

**Manager.** `BuiltIn.Manager` builds `BuiltIn.Config` from that section
(`Config` is pure: the environment is passed in and read only for warnings,
reserved names and `MYDIA_VPN_VPN_INTERFACE`), decides auto-enable, writes the
VPN settings file, and runs one `BuiltIn.Supervisor` tree under the
`BuiltIn.Instances` `DynamicSupervisor`. It subscribes to the reload topic and
restarts the tree only when `Config.restart_key/1` changes, so a save that
leaves the effective config alone restarts nothing, and rqbit resumes its
session after one that does. While the VPN is off its fields are not part of
the key, so editing them never interrupts a running client. A failure while applying is logged and keeps what
already runs. A new tree that fails to start cannot keep the old one (both
need the API port), so the client stays off with a `{:start_failed, reason}`
warning the panel shows, and the manager retries after 5s, 30s, then every
minute until it starts or the config changes. `Manager.current/0` reads a `:persistent_term`, so callers (the
adapter guard, the panel) never wait on the GenServer while an apply is
stopping rqbit; `Manager.await_applied/1` is the call that does wait, for
tests and for callers that need the result of a save.

Auto-enable (`enabled` unset) is on for a new install (`rqbit` on the `PATH`,
no download client of any kind), which the manager records as
`<state_dir>/enabled` so it stays on once the user adds clients, until the
setting says off. An explicit db or env value always beats it. The client never
runs beside another client named `Built-in`, since clients are looked up by
name. `ClientRemoval` and the other config builders must carry
`connection_settings`, or `BuiltIn.managed?/1` reads the built-in client as
unmanaged and the guard below is skipped.

**File selection.** When `WantedFiles` (see "Wanted files and early import"
below) leaves files out before the add, it records the policy's final `auto`
entry so nothing re-selects what it skipped. Otherwise (it kept every file,
or the listing failed or timed out) `BuiltIn.FileSelectionPolicy` deselects
the junk after the add. It (run by `BuiltIn.Policies`
for rows that are in the client and downloading, paused, checking or queued)
deselects junk once per torrent, as soon as the file list is known (a magnet
has none until its metadata resolves; an empty list waits, and so does a
`checking` torrent). `Downloads.FileSelection.keep/1` keeps the files the
importer would take (a video extension that is not a sample, trailer or extra)
and subtitles, and keeps everything when nothing qualifies. The result goes to
the client through the adapter's `set_file_selection` (rqbit's file selection
endpoint) and is recorded in `metadata["file_selection"]`: `auto` with a
`skipped` count (also 0), `auto_pending` with `attempts` after a failure, and
`auto_failed` after the third. `auto`, `manual` and `auto_failed` are final,
and an imported row is never touched. The Downloads drawer's Files panel
(`MydiaWeb.DownloadsLive.FilesPanel`, backed by `Downloads.TorrentFiles`) is
the manual side: a checklist the operator edits until the download is
imported, saved with the `manual` stamp so the automatic pass never overrides
it. At least one video file must stay selected. The save reads `imported_at`
from the database, not the drawer's copy. The policy's final check of the
stored entry, its client write and its stamp, and the save's client write and
stamp, each run under `TorrentFiles.with_selection_lock/2` (a per-download
`:global` lock on this node, never taken inside a database transaction), so a
save cannot land between the policy's check and its write.

**Speed limits.** `download_limit_kib` and `upload_limit_kib` (blank for
unlimited, otherwise 16 KiB/s or more) reach rqbit as its
`--ratelimit-download`/`--ratelimit-upload` flags (`BuiltIn.Engine.args/4`).
They are part of `BuiltIn.Config.restart_key/1`, so a change restarts the
engine. The seeding fields are not: Mydia's policies read them from the
runtime entry, and a seeding-only save never restarts rqbit.

**Seeding env vars.** `MYDIA_TORRENT_SEED_RATIO`, `MYDIA_TORRENT_SEED_TIME`
and `MYDIA_TORRENT_SEED_GOAL_ACTION` map to the three fields through the usual
overlay (`Config.Env.BuiltInTorrentEnv`), as `MYDIA_TORRENT_DOWNLOAD_LIMIT`
and `MYDIA_TORRENT_UPLOAD_LIMIT` do for the limits; an env value wins and
makes the form field read-only.

**Child environment.** rqbit and `torrent-curl` are spawned with every
`MYDIA_VPN_*` variable and Mydia's secrets unset
(`BuiltIn.Config.child_env_unset/1`).

**Runtime injection.** `Mydia.Settings.RuntimeConfig.get_runtime_download_clients/0`
appends `BuiltIn.client_configs/0` to the clients from env and YAML, so the
built-in client is a synthetic `rqbit` row that exists only at runtime. Its
connection settings carry `"managed" => true`.

**Managed guard.** `Mydia.Downloads.Client.Rqbit` wraps every call in
`BuiltIn.guard/1` when the config is managed. A stopped engine, a VPN that is
down or a failed leak check returns `{:error, reason}` with a named reason
instead of a connection error to loopback, so a grab fails with the cause and
`ClientHealth` shows it. Unmanaged rqbit configs skip the guard.

**Unanswered leak checks.** `Vpn` re-runs `LeakCheck` every 60 seconds, which
is roughly 1,440 pairs of requests to the relay a day, so ordinary network
noise has to be tolerated. Each request retries transient failures (Req for
Mydia's side, `curl --retry-all-errors` for the torrent side). A request that
still gets no answer is `{:leak_check_unreachable, _}`, which is different from
`{:leak_check_failed, _}` and `:leak_detected`, the results where an answer
came back and failed the check. On a reverify (gluetun running, same public
and tunnel addresses as the last pass) the engine keeps running through two
unreachable checks in a row and stops on the third. A first check, a changed
address or a failed answer stops it at once. Before this rule, one
`socket closed` from a pooled connection the relay's CDN had dropped stopped
rqbit, and production logged 161 such stops in a day.

**State.** The engine's and the VPN's state, the listen port and the config
warnings live in `BuiltIn.Status`, which broadcasts every change for the admin
panel.

### The VPN settings file and the root loop

Mydia never talks to gluetun's settings API. `BuiltIn.VpnSettings` renders
`/config/gluetun/settings/settings.env` (the `settings/` subdirectory is
mydia's own; see the trust boundary below): `VPN_ENABLED` plus the allowlisted
gluetun keys, one `KEY=value` per line, mode 600, written atomically (temp
file, rename) and only when the bytes changed. Fields whose env var is set are
left out, since env reaches gluetun from the root loop's own environment and is
never copied to disk. A value with a newline is rejected at save.

`docker/vpn-preflight.sh` runs as root from the entrypoint and supervises
gluetun in a loop, every 2 seconds:

1. It snapshots the settings file and hashes the snapshot. On a change, or
   when gluetun exits, it stops gluetun if running and starts it with the
   file's allowlisted keys, then the operator's `MYDIA_VPN_*` env (prefix
   stripped, so env wins), then Mydia's own values.
2. The loop idles while neither `VPN_ENABLED=true` in the file nor
   `MYDIA_VPN_SERVICE_PROVIDER` enables the VPN.
3. Before each start it refreshes the provider's server list with
   `gluetun update -enduser`. The list persists in
   `/config/gluetun/servers.json`. Gluetun only reads `/gluetun/servers.json`
   (the updater hardcodes it) and root never opens a path under `/config`, so
   that file is a root-owned working copy: restored from the config dir as
   mydia when missing and copied back as mydia before each start. Gluetun
   prefers it over its built-in list when newer. Gluetun's built-in list is frozen at its release, and providers
   retire servers: PIA renumbered Montreal and gluetun retried the dead
   addresses forever with `TLS key negotiation failed`. The updater runs
   before gluetun joins the split group, so it reaches the provider while the
   tunnel is down. It is skipped for a day after a success and an hour after
   a failure (stamp in `/run/mydia-vpn/servers-updated`), and never for
   `custom` or `protonvpn` (whose updater needs account credentials). A
   failure only logs; gluetun starts on the list it has. `UPDATER_PERIOD=24h`
   keeps the list fresh while gluetun runs, through the tunnel.
4. After each start or stop it writes `/config/gluetun/loop-status`:
   `hash=<sha256 hex or none>`, `dropped=<comma-separated keys outside the
   allowlist>` and, only when nonzero, `invalid=<n>`, the count of lines that
   are not `KEY=value` with an upper-case key. Invalid lines are counted and
   never echoed, so their text never reaches a file mydia can read.

`BuiltIn.Vpn` learns the hash `Manager` expects and stays `connecting`, with the
engine stopped, until `loop-status` reports that hash. This keeps a gluetun still
running the previous settings from passing the leak check. It then waits for
gluetun to report `running`, runs `LeakCheck`, and opens the engine gate.
`dropped` or `invalid` entries surface as `{:vpn_settings_rejected, keys}`
(`2 invalid lines` for the count); no match within 30 seconds is
`:vpn_apply_timeout`; a write that failed is `{:vpn_settings_write_failed,
posix}`. `Vpn` keeps polling after a timeout.

`BuiltIn.VpnProviders` is the table behind the form: every provider in the
pinned gluetun release, its VPN types, whether it forwards ports and its
`extra_env` (gluetun variables it requires that the form cannot take, such as
client certificates; the form tells the user to set them as `MYDIA_VPN_<NAME>`).
A test fails when `vendor/gluetun/VERSION` changes without the table's recorded
version changing with it.

**Root never touches /config.** `/config` belongs to mydia, so a compromised
BEAM can replace `/config/gluetun`, or any file in it, with a symlink at any
moment. Root therefore never opens a path under `/config`: every read and write
there in `vpn-preflight.sh` runs as mydia through `su-exec`. The settings file
is copied as mydia (5 second timeout, in case the path is a FIFO; 64 KiB cap)
into a root-private snapshot, and root parses only the snapshot, with an
allowlist and no `eval`. State that root must trust lives in `/run/mydia-vpn`
(root, mode 700): the snapshot and gluetun's `auth.toml`.

**Control server lockdown.** Gluetun's default role covers every route no other
role names, and ignores a route list set in `HTTP_CONTROL_SERVER_AUTH_DEFAULT_ROLE`.
The script therefore writes `/run/mydia-vpn/auth.toml` with one apikey role
listing `GET /v1/vpn/status`, `GET /v1/publicip/ip` and `GET /v1/portforward`,
passes it as `HTTP_CONTROL_SERVER_AUTH_CONFIG_FILEPATH` and sets the default
role to `{}`. The key in `/config/gluetun/apikey` can read those three and
nothing else; before this, it could `PUT /v1/vpn/settings`, which accepts
OpenVPN options that run as root.

**Preflight file.** The script writes `/config/gluetun/preflight` on every boot
unless `MYDIA_TORRENT_ENABLED` turns the client off in env. It records
`net_admin`, `tun`, `split_group` and `src_valid_mark`, and only the first
three fail the VPN (`BuiltIn.Preflight`). `src_valid_mark` is informational and
Mydia does not read it yet.

In VPN mode the engine is started with `--listen-ip <tunnel IPv4>`, read from
`ip -4 -o addr show dev <iface>` as the mydia user, so that inbound UDP replies
leave the tunnel from the port the peer contacted. See
`vendor/gluetun/README.md`, "Inbound UDP needs a bound socket".

## Wanted files and early import (rqbit)

`Client.Rqbit` lists a torrent's files before adding it, and
`Queue.ClientSelection` decides which to keep (`WantedFiles.select/2`) and
adds with `only_files`. A selection that keeps everything (`only_files: nil`)
still adds with every listed index, so rqbit widens an older, narrower
selection on a torrent it already manages. Clients without
`list_torrent_files/2`, and a failed listing, add with no selection.
Junk is what `FileSelection.importable?/1` and `subtitle?/1` say it is, the
same rules `FileSelectionPolicy` applies, so the two never disagree on a
sample or an `.nfo`; `WantedFiles` adds the episode rules (skip an owned
episode the search did not target, keep anything it cannot match). The
selection is recorded in the download's metadata:

- `"file_selection"`: `%{"source" => "auto", "skipped" => n}`, `n` (1 or
  more) the files left out, written only when the selection left files out
  (`only_files` set). It is `FileSelectionPolicy`'s final entry, so the
  policy leaves the torrent alone; a manual selection from the Files panel
  replaces it with `manual` as usual. A selection that keeps everything
  (including the every-video-owned fallback) writes no entry, and neither
  does a failed listing (which records none of these keys), so the policy
  deselects junk after the add.
- `"selected_files"`: indices of the files kept.
- `"file_episodes"`: file index (a string) to the single episode id a kept
  video parsed to. Multi-episode and unmatched files have no entry.
- `"skipped_owned_episode_ids"`: episodes dropped because the library already
  has them. `FileImport.detect_partial_pack/2` subtracts these, so such a pack
  is not flagged `partial_pack`.
- `"early_imported_paths"` and `"early_imported_episode_ids"`: what partial
  imports already placed. The full import excludes those paths.

**Choosing files before a manual grab.** "Choose files…" on a torrent result
in a media page's manual search (`MediaLive.Show.FileChoiceEvents`) calls
`Downloads.preview_files/2`, which builds a `Queue.FilePreview`: the duplicate
check, the torrent fetch and the client choice the add would make, the file
listing, and `WantedFiles.select/2`'s picks, with nothing added to the client.
It is offered only when `Downloads.file_choice_available?/0` says the client a
torrent grab would use can select files, and never for an NZB. The operator
adjusts the picks in the folder tree and the confirm passes the preview back
to the grab as `file_preview:` with the chosen `only_files:`. The grab runs
the duplicate check again (time has passed), then reuses the preview's
prepared input, client, listing and peers, so it fetches and lists nothing a
second time. `WantedFiles.manual/3` writes the same keys as above with
`"file_selection" => %{"source" => "manual"}`, so `FileSelectionPolicy` never
touches the torrent, and `"file_episodes"` covers every chosen video, so a
file the operator added can still be imported early. A choice without an
importable video fails with `:no_importable_file`; the modal disables its
confirm for such a choice and refuses one sent anyway, so that failure does
not reach the dialog. The preview, which can hold a `.torrent` body, lives in
the LiveView's assigns only until the modal closes.

Early import is driven by `Downloads.EarlyImport` from `DownloadMonitor`. The
rqbit torrent list carries no per-file data, so EarlyImport fetches per-download
status (`file_progress`) to learn which files are whole. Only files with a
recorded episode and a path that exists on this host are imported early.

A partial `MediaImport` job (`"partial" => true`) is unique on
`[:download_id, :partial]`, so it never swallows the full import enqueued at
completion, and a second partial job is dropped until the first finishes.
Partial jobs run on the single-slot `:early_import` queue, so two of them never
copy at once even when a copy outlasts the 600-second unique period (the
second one's atomic copy would remove the first one's temp file); full imports
stay on `:default`. A full import that starts while a partial job for the
download is executing snoozes 30 seconds (a snooze does not use an attempt).
No Oban Lifeline runs, so a crash, a restart or a queue restarted inside this
node leaves an orphaned `executing` row. An executing partial row counts only
if the `:early_import` queue on this node is running its job id
(`Oban.check_queue/1`'s `:running`), so a job that died mid-run cannot hold
the full import back, while one copying a large file for half an hour still
does. When that lookup fails (the queue is not running), the boot-time rule
stands in: a row attempted before this node booted
(`Mydia.Application.booted_at/0`) is ignored. Partial mode never stamps
`imported_at`, runs `detect_partial_pack` or removes the torrent; a file that
fails stays out of `early_imported_paths` and the full import retries it.
It records its paths through `MetadataKey.modify/2`, under the same row lock
the policies and the Files panel stamp with, so neither side drops the other's
keys.

A manual selection made after the grab does not rewrite `"file_episodes"`.
A file the operator deselects never completes, so it is never imported early;
one they add has no entry and waits for the full import.
