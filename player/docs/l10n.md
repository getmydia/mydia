# Translating the player

The player is translated with Flutter's `gen_l10n` and ARB files. The web UI
uses Gettext instead; see `lib/mydia_web/gettext/README.md`. Translators work
on Weblate (component `player`, see `TRANSLATING.md`). This file is for
developers adding text to the player. Every viewer-facing string under `lib/`
is translated, and a test keeps it that way.

## Where messages live

- `lib/l10n/app_en.arb` is the template. Every message needs a
  `"@key": {"description": "..."}` entry that tells a translator where the text
  appears. `test/l10n/arb_consistency_test.dart` fails without it.
- `lib/l10n/app_es.arb` and `lib/l10n/app_pt_BR.arb` are the shipped
  translations, next to the English template. Keep their keys in the same
  order as the template. A message missing from a translation shows in
  English, and Weblate fills it in.
- `lib/l10n/app_pt.arb` is a stub holding only `{"@@locale": "pt"}`. It exists
  because a regional file needs its base-language file (see below).
- `l10n.yaml` configures the generator. Its output, `lib/l10n/gen/`, is
  gitignored. `flutter pub get` and `flutter test` regenerate it. The release
  Dockerfile copies `l10n.yaml` for the same reason, and `.dockerignore` keeps
  a local `gen/` out of the build context. In devenv the
  `mydia:flutter` task re-runs pub get when the ARB files or `l10n.yaml` change,
  so a pulled translation update does not leave a stale `gen/`.
- Do not hand-edit non-English ARB files once Weblate owns them. Fix wording on
  Weblate, or your edit is overwritten by the next sync.
- A new language needs its name in `localeDisplayName`
  (`lib/l10n/locale_names.dart`), written in that language. Without it the
  picker shows the language code.
- A regional variant (`app_pt_BR.arb`) needs its base language file
  (`app_pt.arb`) next to it, or gen_l10n fails `flutter pub get` and every
  build breaks. When Weblate adds a region-only locale, create the base file
  containing `{"@@locale": "<language>"}`. `test/l10n/arb_consistency_test.dart`
  checks this.

## Writing text

Import `package:player/l10n/l10n.dart` and use `context.l10n`:

```dart
Text(context.l10n.settingsSignOut)
```

- Keys are camelCase, `<area><Purpose>`: `loginServerUrlLabel`,
  `settingsSignOut`. Use the `common` prefix only for words used in two or more
  areas (`commonCancel`).
- One message per whole sentence. Never join translated pieces, word order
  differs between languages.
- Values are placeholders declared with a type in the `@key` entry. For
  example, a plural (the key here is illustrative):

  ```json
  "settingsDeviceCount": "{count, plural, one{{count} device} other{{count} devices}}",
  "@settingsDeviceCount": {
    "description": "How many devices are paired.",
    "placeholders": { "count": { "type": "int" } }
  }
  ```

  Keep the number in the `one` form too: some languages use it for 21, 31 and
  so on.
- Never translate media or user data, text sent by the server, `debugPrint` and
  log text, `Key('...')` values, or product names (Mydia, Plex, Jellyfin,
  Stash, TMDB, TVDB, Chromecast, AirPlay).
- A string that names a button or menu in the web UI must use the web's label
  in that language. See `loginTvStepOpenDevices` and its description.
- Dates and weekday or month names go through `DateFormat` skeletons
  (`DateFormat.yMMMd(localeName)`) in a formatter method of `AppFormatters`.
  Never write month or weekday names by hand.
- Code with no `BuildContext` (a controller, a service) does not call
  `context.l10n`. Take an `AppLocalizations` as an argument and let the widget
  pass `context.l10n` in.
- A new language needs its name in `localeDisplayName`
  (`lib/l10n/locale_names.dart`), written in that language. Without it the
  picker shows the language code.
- A regional variant (`app_pt_BR.arb`) needs its base language file
  (`app_pt.arb`) next to it, or gen_l10n fails `flutter pub get` and every
  build breaks. When Weblate adds a region-only locale, create `app_pt.arb`
  containing `{"@@locale": "pt"}`. `test/l10n/arb_consistency_test.dart`
  checks this. Such a message-free base is a stub: list its language in
  `stubLanguageCodes` (`lib/l10n/locale_resolution.dart`). Stubs are hidden
  from the language picker, never stored or taken from the host, and a device
  or host locale in that language (`pt`, `pt_PT`) resolves to the shipped
  regional variant (`pt_BR`) through `resolveAppLocale`, which every
  `MaterialApp` sets as its `localeListResolutionCallback`.
  `test/l10n/locale_resolution_test.dart` checks that each listed stub holds
  only `@@locale` and that no other empty base is missing from the list.

## Typed values, not sentences

Code with no `BuildContext` (a controller, a service, `core/`, `domain/`) never
calls `context.l10n` and never returns a sentence for the viewer. It returns a
typed value (an enum, a sealed class, a `Duration`, a number) and the widget
words it through `AppFormatters` in `lib/l10n/formatters.dart`: nav rows
(`navDestinationLabel`), stats rows (`statsRowLabel`, `statsValue`), pairing
progress (`pairingStepText`), connection state (`connectionLabel`), quality
delivery (`originalDeliveryText`) and so on. Add a formatter next to the typed
value when you add one.

`currentAppLocalizations()` from `lib/l10n/current_l10n.dart` is only for OS
surfaces with no widget tree at all (an Android notification, the OS biometric
prompt). It follows the language chosen in Settings, else the device. A widget
uses `context.l10n`: it follows the tree, this does not.

### Failures

A `SourceException` (`lib/domain/sources/source_error.dart`) carries a kind,
and either the server's own words (shown verbatim) or a `SourceFault` for a
failure the app recognised. Screens word it with `AppFormatters.sourceError`.
`toString()` and `logText` stay English for logs.

A failure that reaches the screen later keeps its typed value in state and is
worded in `build`: `PlaybackProblem`, `SignInProblem`, `LoginFailure`,
`UpdateProblem`, `DownloadFailure` and `CastFailureKind`.
`DownloadTask.error` is persisted, so it holds `DownloadFailure.encode()`
(`dlf:<code>|<count>|<kind>|<fault>|<detail>`, names rather than indexes); an
older plain sentence decodes as an unknown failure and is shown as written.
Read it through `DownloadTask.failure`.

## The guard

`test/l10n/untranslated_text_test.dart` scans everything under `lib/` except
generated code (`lib/l10n/gen/`, `lib/graphql/`, `.g.dart`, `.freezed.dart`,
`.gql.dart`) and fails on literal English. The scanner
(`test/l10n/untranslated_text_scanner.dart`, tested in
`untranslated_text_scanner_test.dart`) reads string literals passed to
`Text(...)` and to named arguments such as `label`, `labelText`, `hintText`,
`helperText`, `errorText`, `title`, `subtitle`, `tooltip`, `message`,
`semanticLabel` and `text`. It also sees either branch of a ternary, either
side of `??`, and the message argument of `showToast`.

It does not see concatenation, a literal passed positionally to any other
helper, a string built in a variable first, or a failure message assembled in
code. Check those by hand.

`// l10n-ignore <reason>` on a literal's first line skips it, for text that is
not translatable: product names, log text, a stored title built from server
data, resolution names such as `720p`, a format string. Say why in the same
comment. Diagnostics reports pasted into bug reports (the stats Copy text, the
Diagnostics Copy text) also stay English.

`test/l10n/arb_consistency_test.dart` checks that every message has a
description, each translation uses only template keys and placeholders, and
every regional file has its base-language file. It checks keys, placeholders
and base locales, not wording.

## Testing

Widget tests that pump a widget using `context.l10n` need the delegates on
their `MaterialApp`, or it throws:

```dart
MaterialApp(
  localizationsDelegates: AppLocalizations.localizationsDelegates,
  supportedLocales: AppLocalizations.supportedLocales,
  home: ...,
)
```

The test locale is English, so assertions on English text keep working. The TV
tier (`*_tv_test.dart`) only runs with the TV flag, so run it too after
touching text on a screen it covers, one file at a time:

```bash
flutter test --concurrency=1 --dart-define=MYDIA_FORCE_TV=true \
  $(git ls-files 'test/**/*_tv_test.dart')
```

## How the language is chosen

`localeSettingProvider` (`lib/core/settings/locale_setting.dart`) holds a
`Locale?`. `null` means follow the device, which is the default. A choice is
stored under `interface_locale`, and the picker is a row in Settings,
Appearance. A stored tag the app no longer ships falls back to the device
language. The provider is hand-written because
riverpod_generator cannot print `Locale`.

The web player a Mydia instance serves at `/player` follows the web UI
instead: `PlayerController` injects the request's resolved Gettext locale as
`window.mydiaConfig.locale`, and `hostLocaleProvider` maps it to a shipped
player locale (exact match, then the bare language, then English, which is
what the web UI shows for untranslated text). When it is present the stored
choice is never read, because browser storage is shared by every user who
signs in on that browser. Picking a language in the player's settings still
applies for the rest of the session.

The stored language is read asynchronously, so the first frame or two
(including "Loading...") can render in the device language, like the theme
preset.

`StartupSplash` and `StartupErrorApp` sit outside `ProviderScope`, so they
always follow the device language, whatever was chosen in settings.
